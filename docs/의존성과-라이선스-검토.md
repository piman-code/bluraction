# 의존성과 배포 라이선스 검토

2026-10-02 준비 기록이다. 앱 소스의 루트 `LICENSE`는 MIT다. 이는 실제 설치 파일에 포함한 Qt·FFmpeg·HEIF 코덱·Python 등의 재배포 조건을 대신하지 않는다. 현재 최종 Windows 번들의 전수 wheel/DLL·대응 소스·빌드 자료를 검수한 기록은 없으며, 이 문서는 배포 적합 판정이나 `reviewed` 기록이 아니다.

Mac 운영 설치0.7.2는 유지한다. 최신 사용자 직접 승인으로 새 격리 환경 설치를 진행했고 Mac av/OpenCV/pypdf/pillow-heif 실제 검수는 아래에 구분한다. 실제 Windows 환경과 PowerShell/Inno 실행은 미검증이다. 첫 조사는 공식 문서·upstream source를 읽었으며, 공식 PyPI의 Windows x64 표준 CPython3.14 codec wheel3개의 SHA·DLL·license를 정적으로 확인했다. 이 Windows archive들은 설치·DLL 실행·외부 업로드하지 않았다. 과거 없는 backend의 명시적 skip은 라이선스 또는 실제 코덱 통과가 아니다.

## FFmpeg와 HEIF 결합 배포의 선택지

FFmpeg는 기본 LGPL2.1-or-later지만 GPL 부분을 포함하면 전체 FFmpeg의 조건이 GPL로 바뀐다. upstream 현재 PyAV vendor recipe에는 version3와 libx264/libx265 선택이 보이므로 stock wheel을 단순 LGPL로 취급할 수 없다. 이 recipe의 현재 `main`은 exact9.0.2-1 wheel configuration의 대체 증거가 아니다. 실제 export가 Windows `h264_mf`를 선택해도 포함된 GPL codec DLL의 재배포 조건은 남는다. `--enable-nonfree` 구성은 일반 공개 재배포 후보로 채택하지 않는다. [FFmpeg 공식 조건](https://ffmpeg.org/legal.html), [upstream license/configuration 설명](https://raw.githubusercontent.com/FFmpeg/FFmpeg/master/LICENSE.md), [vendor recipe](https://raw.githubusercontent.com/PyAV-Org/pyav-ffmpeg/main/scripts/build-ffmpeg.py)

pillow-heif1.8.0 manifest는 binary wheel을 GPLv2라고 요약한다. x2654.2 header는 GPLv2 또는 이후 버전을 허용하므로 GPLv3 결합 경로를 검토할 수 있다. LGPLv3 Qt/libheif와 함께 쓴다는 사실만으로 stock wheel이 무조건 불가능하다고 결론내리지 않는다. 반대로 그 header 하나로 모든 포함 파일이 GPLv3 선택 가능하다고 확정하지 않는다. 실제 GPL2-only 파일·추가 조건·runtime exception을 전수 확인한다. [wheel manifest](https://raw.githubusercontent.com/bigcat88/pillow_heif/v1.8.0/LICENSES_bundled.txt), [x2654.2 grant](https://raw.githubusercontent.com/Multicorewareinc/x265/4.2/source/x265.h)

| 배포 경로 | 준비할 결합물과 자료 | 결정 조건 |
| --- | --- | --- |
| A. 검수한 stock GPLv3 결합 배포 | 실제 stock FFmpeg+x265와 pillow-heif를 선택하고 적용 가능한 GPLv3 결합 조건을 지킨다. 앱 MIT 저작권/원문을 보존하면서 결합 배포 조건을 별도로 명시한다. 앱·wrapper·FFmpeg·x265·libheif·하위 라이브러리의 정확한 대응 소스, patches, 생성/설치/build scripts 및 notices를 제공한다. | 모든 구성의 GPLv3 호환 grant, 대응 소스 접근/재빌드, LGPL 부분의 수정/교체 조건 및 실제 기능 검증이 확보되어야 한다. 루트 MIT 파일 하나만 넣은 채 결합물을 MIT라고 광고하지 않는다. |
| B. 검수한 LGPL/BSD custom runtime | PyAV를 GPL/nonfree 부분 없는 shared FFmpeg에 맞춰 빌드하고, HEIF는 libheif+libde265+BSD kvazaar 또는 검증된 native encoder 경로를 사용한다. Qt/OpenCV/HEIF에서 포함한 별도 FFmpeg·runtime도 각각 감사한다. | decoder·HEIC encoder·투명도/ICC/회전·chroma·HDR 톤매핑·모든 영상/오디오/추적 기능을 동일 계약으로 입증해야 한다. 해당 native codec 없는 PC에서 기능을 빼거나 JPEG로 바꾸는 대안이 아니다. |

GPLv3 대응 소스는 실제 object code를 생성·설치·실행·수정하는 데 필요한 소스와 제어 scripts를 포함한다. 공개 binary 다운로드에 대응 소스를 함께 안내하고 동등하게 받을 수 있게 준비한다. generic upstream homepage만 링크하지 않는다. LGPLv3는 suitable shared-library mechanism 또는 재결합에 필요한 소스/코드 제공 경로를 두며, 인터페이스 호환 수정 library로 동작하는 조건을 검증해야 한다. sealed EXE나 서명 정책으로 교체를 막지 않는다. User Product의 installation information 요건은 해당 배포 방식에서 적용 여부를 기록한다. 이 문서의 경로 A/B는 최종 license 판정이 아니라 이 조항들에 기반한 구현·증거 계획이다. [GPLv3/LGPLv3 전문을 포함한 upstream COPYING](https://raw.githubusercontent.com/strukturag/libheif/v1.23.4/COPYING)

kvazaar 소스는 BSD3지만 libheif kvazaar plugin의 실제 bit-depth/chroma/size 제한을 확인해야 한다. 현재 plugin source는 지원 chroma를 정하고 다른 입력을 변환하므로 기존444 명시 encode 계약과 동일하다고 가정하지 않는다. native WIC도 HEIF encoder API가 있고 HEVC codec 존재를 조회할 수 있으나 모든 PC에 제공된다는 보장은 없다. 실제 byte 재열기와 alpha·metadata·색상·원본 보존 검사를 통과하기 전 대체 경로를 완료로 표시하지 않는다. [kvazaar license](https://raw.githubusercontent.com/ultravideo/kvazaar/master/LICENSE), [libheif plugin](https://raw.githubusercontent.com/strukturag/libheif/v1.23.4/libheif/plugins/encoder_kvazaar.cc), [Microsoft HEIF codec](https://learn.microsoft.com/en-us/windows/win32/wic/heif-codec)

HEIC 읽기·출력과 HDR 지원은 전체 목표에 남는다. optional HEIF backend는 Mac 격리 runtime에서 fake 정책9·실제 codec2를 통과했으나 Windows 실행과 HDR 톤매핑은 미완료다. 과거 codec skip을 새 통과로 옮기지 않았다. 영상 HDR은 RGB 변환 전 transfer/bit-depth와 톤매핑 검증이 아직 없으므로 HEIF와 같은 명시 거부가 있다고 가정하지 않는다. 더 편한 라이선스를 고르기 위해 alpha를 흰색으로 바꾸거나 HDR/추적/오디오/지원 형식을 제외하지 않는다. codec 특허나 OS/Store codec 재배포 권한은 오픈소스 copyright license와 별도이므로 실제 대상 배포에서 적용 여부를 기록한다. OS encoder 사용만으로 이 부분이 자동 해결되는 것은 아니다. [Qt codec 권리 안내](https://doc.qt.io/qt-6.11/qtmultimedia-index.html), [FFmpeg 공식 조건](https://ffmpeg.org/legal.html)

## 실제 wheel/DLL 감사를 수행할 순서

1. 승인한 격리 환경에서만 정확한 wheel을 확보한다. package filename·URL·SHA256·platform tag·Python ABI·RECORD·dist-info licenses와 pin을 기록한다. transitive wheel과 interpreter/build tools도 별도 catalog로 고정한다. source tree나 사용자 미디어를 서버에 올리지 않는다.
2. wheel을 파일별로 조사하고 최종 onedir를 다시 전수 조사한다. 숨김 파일·`.pyd`·`.dll`·Qt plugin·HEIF encoder/decoder plugin·`.libs`·MinGW/MSVC/BLAS/runtime까지 포함한다. package distribution과 실제 file을 대응시켜 중복 FFmpeg도 DLL SHA/ABI별로 구분한다. PyAV·QtMultimedia·OpenCV FFmpeg는 같은 이름이라는 이유로 합치지 않는다.
3. 실제 승인된 runtime에서 `av.library_versions`, `cv2.getBuildInformation()`, `pillow_heif.libheif_info()`를 보관한다. 정확히 로드한 DLL의 `avcodec_configuration/license`, `avformat_configuration/license`, `avutil_configuration/license`, `swscale_configuration/license`, `swresample_configuration/license` 결과와 파일 경로/SHA를 연결한다. 등록된 codec 목록과 실제 실행 가능한 encoder는 구분하며 `h264_mf`/HEVC의 실제 output reopening까지 확인한다. PyAV metadata만으로 누락된 모든 FFmpeg configure/license를 추측하지 않는다.
4. 각 DLL의 대응 source version/commit·원본 archive SHA·로컬 patches·configure/CMake flags·toolchain·build scripts·하위 library source를 확보한다. stock vendor 소스를 재빌드할 수 있는지 확인하고 공개 source payload와 binary의 대응표를 만든다. `main` recipe만으로 이미 받은 wheel을 재현한다고 적지 않는다.
5. 기능 검사와 license 조건을 각각 검수한다. actual PDF parser7·actual HEIC2·현재 영상13(실제 영상10+행렬 정책3)은 skip 없이 실행하고, frozen onedir에서도 HEIC/영상/추적/오디오·cancel·원본 보존을 확인한다. LGPL 교체/재결합은 검수용 복사본에서만 시험한다. 실제 Windows 파일 패널/Explorer·설치·서명/사용자 실행은 별도 증거다.
6. 동일 최종 bytes의 manifest와 검수 기록이 생긴 뒤 ZIP/installer를 만든다. 구성 변경은 이전 record에 덧붙여 승인 처리하지 않고 새 manifest에 대응시킨다. 같은 최종 bundle로 설치/원본 보존/출력과 다운로드 SHA를 확인한다.

이 절은 최종 후보의 실행 계획이다. 아래 codec3 archive 정적 inventory는 확보했지만 전체 번들 inventory·corresponding source payload·approved record는 아직 완성하지 않았다.

## 최종 payload와 catalog 요건

`-LicenseMaterials`로 공급할 실제 자료 폴더는 `NOTICE.txt`, `dependencies.json`, 원문 license·build/configuration/source 증거를 가진다. `dependencies.json` 루트는 `{"dependencies":[...]}`이고 각 항목은 `id`, `version`, `license`, `redistribution_review`, `license_files`, `evidence_files`를 갖는다. 두 배열은 자료 폴더 안의 실제 비어 있지 않은 파일 상대 경로다. placeholder license나 빈 evidence를 만들어 gate를 통과시키지 않는다.

현재 두 wrapper의 필수 id는 `python`, `pyside6`, `qt`, `pdfium`, `pyav`, `ffmpeg`, `opencv`, `pillow`, `numpy`, `pyinstaller`, `pypdf`, `pillow-heif`, `libheif`, `heif-codecs`다. 그 외 실제 포함 decoder/encoder/FFmpeg 별도 구성/runtime도 추가 항목 또는 명확한 file catalog로 분해한다. 자료 inventory의 pypdf6.19.0/pillow-heif1.8.0/Pillow12.3.0은 두 wrapper가 exact version을 확인한다. 새 후보의 interpreter는 별도 metadata gate로 모든 선언 pin을 대조한다. 자료 inventory의 나머지 nonempty version 검사나 interpreter metadata만으로 actual wheel/DLL/license 일치를 선언하지 않고 reviewer가 최종 file catalog와 대조한다.

각 dependency의 evidence는 최소한 다음 정보를 연결해야 한다.

| 증거 | 구체 내용 |
| --- | --- |
| provenance | 배포 filename/URL/SHA·원본 license 파일·source tag/commit·platform/ABI·추가 grant/exception |
| binary catalog | bundle-relative file paths·SHA·실제 version·link/plugin 관계·추가 DLL·하위 attribution |
| build/source mapping | exact source archive SHA·patch·configure/build flags·toolchain·재빌드 안내·소스 다운로드 경로 |
| redistribution review | 선택 license expression·GPL 결합 범위·LGPL 교체/재결합·source/notice 제공·미해결 사항과 판정 |
| capability evidence | 실제 decoder/encoder/CSRT 및 required codec test logs, frozen bundle 결과·host/version/input/output hashes |

최종 공개 후보는 Windows portable ZIP/installer EXE와 Mac 후보 ZIP/DMG, binary SHA 목록, exact bundle manifests, 앱 source archive, 적용 license 전문·저작권/NOTICE, 의존성 catalog, 대응 dependency source archives/patches/build recipes, 한국어 빌드·설치·제거·복구 안내와 알려진 제한을 포함한다. binary마다 source/catalog를 구분하고 LGPL/GPL 소스 다운로드 위치를 해당 다운로드에 연결한다. 서명은 실제 상태를 표시하고 보안 설정을 끄는 절차를 넣지 않는다. source payload가 준비되었다는 표현은 archive 실물과 SHA/접근 검수가 있을 때만 쓴다.

검수 기록은 `status=reviewed`, `version`, `bundle_manifest_sha256`, `reviewed_by`, `reviewed_at`, `dependencies`를 실제 findings로 채운다. `license-review.example.json`은 pending 예시이고 자동 승인 자료가 아니다. 자료 파일 존재 검사와 source/codec tests는 사람의 license 적합 판단을 대체하지 않는다.

현재 build_package.ps1의 `-PrepareForReview`는 실제 자료가 있을 때 새 private onedir와 manifest만 만든다. `-FinalizeReviewedBundle`은 같은 bundle bytes와 record를 확인한 뒤 ZIP을 만들고, installer wrapper도 exact manifest/record 및 전체 파일을 컴파일 전후 재검사한다. hidden/unlisted/reparse 항목을 포함한 변경은 거부한다. 이 준비 단계는 설치·릴리스 공개 승인이 아니며 기존 승인 범위에서 가능한 개발/검수는 계속한다. 별도의 불필요한 단계별 승인 규칙을 추가하지 않는다.

현재 판정은 **자료 준비 중·exact binary 배포 검수 미완료**다. 기능 범위는 유지하고 경로 A/B를 실제 바이너리·소스·코덱 증거로 선택한다. 최신 사용자 승인으로 검수 후 공개를 계속하되, 최종 구체 payload 검수와 실제 공개/원격 확인 전에는 Release 완료를 표시하지 않는다.

## Windows codec3 wheel 정적 실측 — 설치·런타임 검수 아님

2026-10-02 공식 PyPI SHA에 일치하는 파일을 로컬 QA에서 읽었다. PyAV19의 cp312-abi3-win_amd64, pillow-heif1.8의 cp314-cp314-win_amd64, OpenCV4.14의 cp37-abi3-win_amd64다. Python3.14의 표준 ABI/x64 후보 조사이며 free-threaded/ARM64 선택본의 증거가 아니다. 최종 설치 파일에 들어간 DLL이나 실제 사용 가능한 encoder를 뜻하지 않는다. [PyAV 파일](https://pypi.org/project/av/19.0.0/#files), [pillow-heif 파일](https://pypi.org/project/pillow-heif/1.8.0/#files), [OpenCV 파일](https://pypi.org/project/opencv-contrib-python-headless/4.14.0.94/#files).

PyAV wheel은 FFmpeg DLL과 x264165/x265·MinGW DLL을 포함한다. 정적 configuration 문자열에는 libx264/libx265/version3가 보이지만 enable-gpl은 보이지 않고 license 문자열은 LGPL3이다. 이 관계는 vendor source·patch·build 및 실제 로드한 library configuration/license와 대응하기 전 미해소다. 라이선스 문자열 하나나 wrapper BSD만으로 결합물 적합성을 승인하지 않는다.

pillow-heif wheel의 실제 bundled notice는 GPLv2와 libheif/libde265 LGPLv3를 함께 표시한다. x2654.2 upstream header에는 GPL2-or-later 선택 문구가 있지만 exact DLL의 소스/빌드 대응과 전체 결합 조건은 남아 있다. OpenCV의 videoio FFmpeg DLL은 PyAV와 별개 SHA·구성·third-party notice로 조사한다.

세 archive는 설치하거나 DLL을 추출·실행하지 않았다. 전체 대응 소스/NOTICE/build recipe, 실제 Windows loaded module의 경로/SHA/configuration/license, Qt·Python 등 나머지 구성 및 최종 onedir/installer inventory와 runtime 검수를 완료해야 한다. 정적 inventory는 `reviewed` license record의 대체물이 아니다.

정적 조사 후 PyAV19가 참조하는 vendor9.0.2-1의 tag commit `bac889417e26be29615cb6a3f38318151fed55cd` 및6개 build/patch 원문을 SHA·Git blob과 대조했다. 해당 `ffmpeg.patch`는 libx264/libx265를 GPL 목록에서 VERSION3 목록으로 옮긴다. 포함 codec의 라이선스 grant를 변경하거나 재라이선스한 증거가 아니므로 DLL의 LGPL3 문자열과 enable-gpl 부재만으로 GPL 코드가 없다고 판정하지 않는다. exact wheel의 대응 소스·patch 적용/build 로그·toolchain·DLL mapping은 여전히 미완료다. [PyAV19 vendor 선택](https://github.com/PyAV-Org/PyAV/blob/v19.0.0/scripts/ffmpeg-latest.json), [exact vendor patch](https://raw.githubusercontent.com/PyAV-Org/pyav-ffmpeg/9.0.2-1/patches/ffmpeg.patch), [FFmpeg 공식 조건](https://ffmpeg.org/legal.html).


## 후속 실물 자료 준비 — 최종 번들 검수 전

공식 해시와 일치하는 Qt6.11.1 Windows wheel4개와 Python3.14.8 GIL x64 후보·NumPy2.3.5·Pillow12.2/별도12.3 후보·PyInstaller6.22.3 및 transitive wheel/source22개를 정적으로 확인했다. 이 Windows 자료는 설치·실행한 runtime이나 최종 번들 목록이 아니다. 개발 목록의 Pillow는 공식 수정판12.3.0으로 갱신했다. 최신 직접 승인으로 일반 격리 설치 대기는 해소됐으며 전역 환경은 보존한다. 이전12.2 회귀를12.3 통과로 옮기지 않고, 새 Mac 실제 runtime 검사는 아래와 `검증-상태.md`에 구분한다. 정확한 Windows wheel 및 native DLL/third-party 조합에서 실제 출력/라이선스 검수는 계속 필요하다.

Qt archive의 독립 license 이름 파일은 commercial 안내뿐이고 open-source metadata 선택은 별도다. 실제 배송 구성에 LGPL/GPL 전문과 third-party notices·대응 source/build 자료가 필요하다. 현재 QtGui hook의 platforminputcontexts 수집은 실제 qtvirtualkeyboardplugin.dll→Qt6VirtualKeyboard.dll로 이어질 수 있으며, 해당6.11.1 모듈은 GPL3-only/commercial이다. QWidget 앱의 미사용 plugin을 개별 제외하거나 GPL 경로를 충족하는 방안을 실제 bundle·한글 IME 검수와 함께 결정한다. native DLL 수집은 Python exclude-module만으로 차단됐다고 가정하지 않는다. 제품 hook은 아직 수정하지 않았다. [정확한 QtVirtualKeyboard 소스](https://raw.githubusercontent.com/qt/qtvirtualkeyboard/v6.11.1/src/virtualkeyboard/qvirtualkeyboardinputcontext.cpp), [PyInstaller module map](https://raw.githubusercontent.com/pyinstaller/pyinstaller/v6.22.3/PyInstaller/utils/hooks/qt/_modules_info.py).

Qt Multimedia의5개 FFmpeg DLL은 정적으로7.1.3/MSVC/shared 및 동일 configure를 확인했으며 PyAV ABI63이나 OpenCV DLL과 다른 구성이다. QtPdf 소스의 상위 Chromium gitlink와 DEPS의 PDFium pin을 연결하고 PDFium license 원문을 확보했다. 실제 wheel release build·Qt patches·GN feature별 전체 PDF attributions와 포함 dependency의 source/notice는 남는다.

PyAV vendor 고정 recipe의 source archive15개와 license text61개를 해시로 확인했고 vendor 자산과 wheel의23DLL 코드 섹션이 같았다. 전체 파일은8개만 같고 repair 가능성과 양립하는 차이를 별도 기록했다. 실제 변환 원인은 아직 확정하지 않았다. MSYS 런타임은 공식 과거 package/source·서명을 정적으로 추가 조사 중이며, strip 변환을 포함한 전체 build 대응을 완료한 것은 아니다. 코드 섹션 일치나 archive 존재만으로 GPL 구성·전체 배포 적합성을 승인하지 않는다.

NumPy wheel의 OpenBLAS/LAPACK/GCC runtime exception 고지, PyInstaller bootloader exception과 runtime-hook Apache 조건, setuptools vendored LGPL 구성, Pillow의 합친 고지·build SBOM도 확인했다. Pillow generic SBOM에 optional GPL 항목이 있다는 이유만으로 Windows wheel에 그 DLL이 들어 있다고 단정하지 않는다. 정확한 Windows workflow·binary·feature와 대응한다. Pillow12.2의 공식 보안 수정 후보는12.3이며 후보가 가진 내부 third-party 조합도 달라 실제 alpha/crop/ICC/HEIF 회귀가 필요하다. 현재 제품에서 고지된 공격 조건으로 이어지는 호출 경로는 정적으로 확인하지 못했고, 기존12.2가 수정됐다는 판정을 하지 않는다. [Pillow12.3 변경](https://pillow.readthedocs.io/en/stable/releasenotes/12.3.0.html).

후속 정적 자료는 private QA에 보존한다. 최종 공개 자료는 실제 bundled 파일별 source/notice와 검사 결과를 별도로 선별해 준비하며, 전체 QA archive·빌드·백업을 공개하지 않는다. 현재 exact Windows bundle과 reviewed redistribution record는 여전히 없다.


MSYS 공식 서명 자료의 추가 정적 검토에서 gcc-libs16.1.0-5/libiconv1.19-1/zlib1.3.2-2 후보의4DLL 모든 section 해시가 vendor와 일치했고, 해당 source3의 PKGBUILD 해시도 binary BUILDINFO와 일치했다. 전체 DLL 파일은 일치하지 않는다. 공식 고정 keyring을 별도 QA GPG homedir에서 사용한10개 package/source 서명 검증은 유효했으며 사용자 key/trust 설정은 바꾸지 않았다. 이는 source 대응 일부의 증거이고 배포 적합성 전체 승인이 아니다.

winpthread는 두 공식 서명 후보 모두 vendor 코드/컴파일러와 달랐다. 공식 vendor 고정 커밋의 실제 Windows MINGW64 workflow와 release run/job은 확인했으나 상세 job 로그는 GitHub403 관리자 권한 제한으로 확보하지 못했다. 날짜나 최신 버전만으로 다른 runtime을 대응 소스로 대체하지 않는다. 정확한 package/build/strip provenance를 확보하거나 별도의 고정 toolchain·소스·라이선스에서 재현 빌드해 실제 기능을 다시 검증해야 한다. 현재 DLL을 교체하거나 배포하지 않았다.

승인 후 새 Mac arm64 venv에는 개발7개 exact pins와 Qt transitive3개를 설치했다. wheel10개의 공식 PyPI 파일명/크기/SHA를 대조한 뒤 local wheelhouse에서 no-index 설치했고 전역8개 metadata/운영 앱 binary를 보존했다. 실제 PyAV19 FFmpeg ABI63·OpenCV4.14 CSRT·heif1.8 libheif1.23.4/x2654.2/libde2651.1.3·Pillow12.3·pypdf6.19 경로를 기록했다. 실제 출력 검사 결과는 Mac 실행 범위이며 Windows wheel 대응 source/NOTICE나 최종 배포 적합성 증명이 아니다. 추가 승인 없는 진행과 라이선스 검수의 완료 여부를 구분한다.
