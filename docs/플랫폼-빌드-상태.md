# 플랫폼 빌드 상태

## 새 Windows 소스 빌드와 실행 범위

`build-recipes/windows-owned-ffmpeg/`는 stock FFmpeg9.0.2 GPL3 shared MediaFoundation과 PyAV19 source wheel을 새 일회성 작업 폴더에 만든다. 공식 archive/build-wheel SHA를 pin하고 compiler package closure는 다운로드 전에 lock·서명을 확인하며, 새 DLL에서 MSVC import libraries를 생성하고 delvewheel로 repair한다. MSVC/SDK는 실제 worker의 version/exeSHA를 획득하므로 다른 날의 같은 toolchain 재현이 완료됐다고 주장하지 않는다.

PythonAST·Bash 구문과 독립 source review만 완료했다. 실제 Windows PowerShell parse/build/MF software encode·VFR/PCM/MP4·actual loaded DLL census는 후속 CI 결과로 판정한다. 첫 core build가 HEIF·추가 codec·Qt/IME·모든 미디어 형식을 완료하지 않는다. 실제 DLL별 corresponding source·notice·relink 자료가 연결되기 전 sourceComplete=false다. 아직 Windows 배포본/Release가 아니다.

기존 `Verify Mac and Windows candidates` workflow의 dispatch에서 `owned_windows_ffmpeg=true`로 이 경로를 실행한다. `target_platform=windows`는 일반 Windows 회귀만 선택하며 기본값은 all이다. 두 경로의 concurrency group은 달라서 한 검사 때문에 다른 검사를 취소하지 않는다. public Actions artifact에는 logs/reports/manifest만 공개한다. 깨끗한 Windows 설치·실제 앱 실행/Explorer/file-panel 사용자 검수는 별도로 남는다.

Windows 후속 수리는 로컬 `7e40a14`에 기록했다. 검수된 후속 소스 `56b474f35ddcaaf2e6caf187b79c7e09e5e237fb`는 GitHub 개발 브랜치에 공개했다. 첫 CI 36953462804의 portable 검사만 통과했고 Mac 도구 준비·Windows source fingerprint 검사에서 실패했다. 현재 수정과 실제 재검사 결과는 `검증-상태.md`에서 구분한다.
- 후속 CI `36955897197`의 Windows 실제 PDF/HEIF9 및 H.264/CSRT 등록은 통과했다. 전체 회귀는 portable 저장 race 검사에서 실패했고, Mac은 도구 설치 이후 shell 단계에서 실패했다. 현재 수리와 시간 계약 metadata 검사도 포함한 로컬 작업본은 후속 CI에서 소스 SHA를 다시 대조해야 한다. 실제 패키지/깨끗한 사용자 설치 통과는 아니다.
- 세 번째 CI `36959291323`는 공개 `03efb4d`에서 Windows PDF/HEIF9·Packaging10·portable51통과/1skip·Job Object2를 확인했다. Mac 도구 준비·제품 컴파일도 성공했다. 이어 검사 도구 UTF-8/경로 오류와 Mac 테스트 매크로 호환성 오류가 발생하여 전체 native 회귀·패키징은 미완료다. 수정된 검사9묶음92개는 Mac native API에서 통과했으며 새 실제 CI를 이어 실행한다.
- 네 번째 CI `36961310075`의 Windows 검사 runner는18통과/Unix1skip으로 완료됐다. asset19 다음 engine48통과/PNG2오류였으며 native handle 수리를 진행했다. Mac은 AppKit 내부 DropValidation3 통과 뒤 Swift Testing102 완료 문구 판독에서 중단됐다. 전체 native 회귀·설치 패키지 검수는 아직 미완료다.
- 다섯 번째 CI `36963690835`는 공개3927306에서 Windows engine50/export lifetime15/frame inventory23을 포함한13묶음을 통과했다. 이후 UI43의 잘못된 PNG 입력 장치/Monospace 해석을 수정했고 새로운 Windows 실행을 기다린다. Mac은 Drop3·Editor10·Groups8을 통과했으며 Image8 중1 encodeFailed를 형식·픽셀 진단으로 조사한다. 미완료를 skip 또는 지원 형식 축소로 바꾸지 않는다.
- Windows는 `platforms/windows/bluraction/`의 별도 Qt 어댑터이다. 기존 Mac
  `Sources/BlurAction/`와 `scripts/build_app.sh` 경로를 유지한다.
- `shared/`는 v1/v2와 개발 중인 v3 시간축 데이터 계약·경로 재연결·합성 자료이다. v3 앱 시간축 연결은 아직 보류한다. 앱 구현과 렌더러는
  각 플랫폼의 책임이다. Mac에서 Qt 검사가 통과해도 Windows 검수로 표기하지 않는다.

## Mac 후보

```sh
python3 scripts/verify_mac.py
# 필요한 한 묶음만 검사할 때:
python3 scripts/verify_mac.py --suite PortableProjectCompatibilityTests
./scripts/build_app.sh --build-only --no-install
```

후보는 `.build/BlurAction.app`에 생긴다. `/Applications/BlurAction.app`이나
루트의 이전 `BlurAction.app`을 이 명령으로 교체하지 않는다. 빌드 후 후보를
별도 이름으로 복사하고 버전·서명·파일 manifest·출력을 그 후보로 검수한다.
현재 소스18묶음138 내부 회귀와 별도 AppKit 검수 뒤 만든 후보는 `BlurAction-0.8.0-20261002-053145.app`이다. 이전 후보의 통과를 옮기지 않았으며 새 빌드 입력·바이너리·서명 manifest를 별도로 기록했다. 현재 ad-hoc 서명이며 Developer ID 서명·공증 통과 증거는 없다. 실제 Finder/파일 패널·깨끗한 OS 사용자 실행도 남는다.

## Windows 개발·패키징 준비

아래 **패키지 생성·installer 절차는 Windows에서 아직 실행하지 않았다**. 후속 실제 Windows Server2025 CI는 `-VerifyRuntimeOnly`의 pin 검사와 actual backend9검사 모두 통과했다. 전체 회귀는 이후 portable 저장 검사에서 중단됐고 패키지 생성에는 도달하지 못했다. 그 공개 버전의 PowerShell runtime 경로는 실행됐지만, 새 family runner의 backend9와 Windows Job Object2는 세 번째 CI에서 실행됐으나 전체 Qt/영상 family와 패키징은 아직 미도달이다. 현재 로컬
Mac에는 PowerShell/Inno compiler가 없어 새 `.ps1`을 로컬 파싱·실행하지 않았다.
Mac의 Qt 합성 검사 결과는 Windows 패키징·설치·사용 검수 증거가 아니다.
저장소 루트의 Windows PowerShell에서, 이미 승인한 격리 Python과 실제
라이선스 자료 경로를 지정한다. 이 절차는 의존성이나 도구를 설치하지 않는다.

```powershell
$CandidateVersion = '0.8.0-dev1'
$CandidatePython = 'C:\approved-env\Scripts\python.exe'
$CandidateDirectory = Join-Path (Get-Location).Path ".build/windows-packages/$CandidateVersion"
$LicenseMaterials = 'C:\reviewed-candidate\dependency-materials'
$LicenseReview = 'C:\reviewed-candidate\license-review.json'

# 내부 검사: Qt 환경은 자식에만 지정하며 전역 환경은 바꾸지 않는다.
& $CandidatePython -c "import subprocess,sys; subprocess.run([sys.executable,'-m','unittest','discover','-s','Tests/PortableProjectTests','-v'],check=True,timeout=120); subprocess.run([sys.executable,'-m','unittest','discover','-s','Tests/VerificationRunnerTests','-v'],check=True,timeout=120)"
if ($LASTEXITCODE -ne 0) { throw 'Portable or verification-runner tests failed or timed out.' }
& $CandidatePython scripts/verify_windows.py --timeout 300
if ($LASTEXITCODE -ne 0) { throw 'Qt/media family failed or did not complete.' }

# 실제 notices/증거가 있어야 새 onedir와 manifest를 준비할 수 있다. ZIP은 만들지 않는다.
./platforms/windows/build_package.ps1 -Python $CandidatePython -Version $CandidateVersion `
  -Destination $CandidateDirectory -LicenseMaterials $LicenseMaterials -PrepareForReview

# 여기서 중단해 dist/BlurAction의 실제 DLL/codec/license를 검수한다.
# exact bundle-manifest.json SHA와 version에 연결된 reviewed record를 작성한 뒤에만 실행한다.
# 기존 onedir를 재빌드하지 않고 같은 bytes로 ZIP을 만든다.
./platforms/windows/build_package.ps1 -Version $CandidateVersion `
  -Destination $CandidateDirectory -LicenseReview $LicenseReview -FinalizeReviewedBundle

# 같은 reviewed bundle로 설치 EXE를 컴파일한다. compiler가 없으면 승인 범위의 격리 도구 경로/버전/복구안을 기록한다.
# OutputDirectory는 존재하지 않는 새 폴더여야 한다. installer를 실행하는 명령은 아니다.
./platforms/windows/installer/build_installer.ps1 `
  -Bundle (Join-Path $CandidateDirectory 'dist/BlurAction') `
  -BundleManifest (Join-Path $CandidateDirectory 'bundle-manifest.json') `
  -LicenseReview $LicenseReview -Version $CandidateVersion `
  -OutputDirectory (Join-Path (Get-Location).Path ".build/windows-installers/$CandidateVersion")
```

`-PrepareForReview`는 새 출력 폴더를 요구한다. 생성되는 위치는 지정한
`$CandidateDirectory/dist/BlurAction`과 `$CandidateDirectory/bundle-manifest.json`이다.
검수 후 같은 directory를 `-FinalizeReviewedBundle`에 넘긴다. 자료·검수 기록 없이
ZIP/installer gate를 통과시키지 않으며 `license-review.example.json`의 pending
예시는 승인 기록이 아니다. 설치 wrapper의 `-Compiler`는 필요할 때 이미 설치된
ISCC.exe 경로를 지정하는 선택 인자이며 도구를 설치하지 않는다.

실제 `LicenseMaterials`에는 `NOTICE.txt`, `dependencies.json`, 각 의존성의
원문 라이선스와 bundled binary/build 증거가 있어야 한다. inventory의 각 항목은
`id/version/license/redistribution_review/license_files/evidence_files`를 기록한다.

후보를 만들기 전에 지정한 Python의 distribution metadata를 `requirements-dev.txt`와
`installer/requirements-packaging.txt`의 모든 exact pin과 대조한다. 누락·다른 버전은
오류로 중단한다. `-VerifyRuntimeOnly`는 개발 runtime 목록만 검사하며 PyInstaller를
요구하지 않는다. metadata 검사는 설치·native import·라이선스 적합 판정·실제 codec
검수를 수행하지 않으며, 뒤의 실제 PDF/HEIF 검사와 최종 번들 검수를 대체하지 않는다.
Pillow12.3.0은 Mac 격리 runtime에서 실제 회귀를 확인했다. Windows 회귀·최종 번들 검수는 미검증이다.

Qt/PDFium·Python·PyAV/실제 FFmpeg DLL·OpenCV·Pillow·NumPy·PyInstaller와 추가
codec을 exact bundle 대상으로 검수해야 한다. 파일 존재 검사는 재배포 적합성
판정이 아니다. PyAV wrapper 라이선스만으로 FFmpeg의 GPL 구성 요소를 허용하지
않으며, HEIC decoder/encoder도 실제 codec과 조건을 검수하기 전 bundle에 넣지 않는다.
현재 완성된 라이선스 자료와 exact bundle 검수 기록은 없다.

두 스크립트는 숨김 파일을 포함한 전체 파일을 manifest와 대조하고 root·상위
경로·하위 디렉터리/파일의 reparse 경로를 거부한다. ZIP 생성과 ISCC 컴파일
전후에 bundle 파일 지문 및 manifest/review bytes를 다시 확인한다. 변경되면
결과를 검수 완료로 받아들이지 않는다. 패키징의 내부 검사는 portable 120초,
Qt/media 900초 제한이며 예외에도 기존 `QT_QPA_PLATFORM`을 finally에서 복원한다.

새 의존성 설치는 별도 승인한 격리 환경에 한정한다. Windows용 고정 wheel과
실제 포함 DLL, PyInstaller/Inno 존재·버전을 확인해야 한다. 로컬 Mac에서 준비한
소스와 스크립트만으로 Windows 설치·실행을 선언하지 않는다. 설치 EXE 준비
코드는 있지만 실제 Windows 컴파일·깨끗한 사용자 설치·시작 메뉴 실행·Explorer
drop·출력 검수·코드 서명·HEIC codec 검증은 아직 남아 있다. 개발 실행은 같은
승인한 interpreter로 `& $CandidatePython -m platforms.windows.bluraction`을 사용한다.

실제 지원 완료 표기는 설치·사용 검수를 통과한 OS와 아키텍처에 한정한다.
Windows11 x64를 우선 검증할 계획이며 Windows10·ARM64·Intel Mac은 별도
검증 전 지원 완료로 선언하지 않는다. 기존 미디어 형식은 조용히 제외하지
않고 구현/라이선스/검증 차이를 기능표에 남겨 사용자 결정이 필요한 경우 제시한다.

## 공개 경계

QA 전체 폴더, `.build`, 개인 자료, 원본, 백업은 공개하지 않는다. 최신 사용자
직접 승인으로 검수 후 공개의 단계별 추가 승인 대기는 해소됐다. 공개 직전에
실제 Git 전송 목록과 릴리스 파일·브랜치·커밋·버전·SHA-256 및 라이선스를 확인하고
비밀값·민감정보 검사를 다시 한 뒤 push/PR/merge/Release를 실행한다. 이 문서와 스크립트를 준비한 것만으로
패키지 검수나 최종 Goal 완료를 뜻하지 않는다.

승인 후 Mac arm64 전용 `.build/windows-dev-env`에 개발7개 exact pin과 Qt
transitive3개를 공식 wheel SHA와 대조해 설치했다. 전역 Python/운영 앱은
보존했으며 이 새 폴더 제거로 복구한다. 새 Pillow·실제 PDF/HEIF·PyAV/CSRT/
VideoToolbox 검수 범위와 초기 실패·수리는 `검증-상태.md`에서 구분한다.
Mac 격리 runtime 결과는 Windows 통과로 대체하지 않는다. 실제 Windows CI의 PowerShell/runtime/backend 실행과 실패는 별도 기록했으며 패키지 생성·설치나 최종 대응 source/NOTICE 완료는 아니다.

검토용 Windows onedir 자료는 저장소 `platforms/windows/installer/license-materials/`에 준비했다.14개 ID의 nonempty 고지/근거만 확인됐으며 최종 재배포 검수는 pending이다. 실제 Windows에서 exact pins/backend/full families를 통과한 뒤 `-LicenseMaterials "$PWD/platforms/windows/installer/license-materials" -PrepareForReview`로 새 후보를 만든다. CI workflow_dispatch에서도 같은 상대 경로를 전달할 수 있다. 이 단계는 private 후보와 manifest만 생성하며 기존 설치·공개 ZIP/installer를 만들지 않는다. 최종 bundle SHA와 actual DLL/license/source 대응을 확인한 별도 reviewed record가 있어야 finalize한다.

후속 CI36966564894는 Windows8묶음148개를 통과한 뒤 잘못된 PDF 파일 잠금에서 중단했다. PDF input을 직접 소유한 QFile로 바꾸고 close 오류에도 device 해제를 보장한 새 소스는 로컬58개만 확인됐으며 실제 Windows의 새 결과는 아직 없다. Mac ImageIO 진단 SIGSEGV는 단계별 flush 기록으로 조사 중이다. 별도 진단 실패에도 mandatory native product 회귀를 실행하며, 진단 실패 자체를 성공으로 처리하지 않는다. 신규 owned decoder/정확 시각 provider의 정리·denied seek fallback 보완은 production 영상 재생/오디오/출력 완료가 아니다. 새 source-build wheel 경로는 compiler/runtime/repair 및 대응 소스가 묶인 일회성 Windows 후보로 검수하며 기존 wheel 재현이나 전체 형식 완성으로 표시하지 않는다.
