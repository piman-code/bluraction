# 렌더링과 프로젝트 호환 계약

2026-10-02 현재 소스 기준이다. 같은 프로젝트의 원본·영역·시간·페이지를 두 OS에서 같은 의미로 해석하는 것이 목표다. 저장 데이터의 호환, 렌더링 결과의 비교, 실제 OS에서의 사용 검증을 각각 확인해야 한다. 이 문서는 지원 범위를 줄이거나 출시 완료를 선언하지 않는다.

현재 운영 Mac은 0.7.2이며, 이후 Mac 소스와 Windows 어댑터는 개발·검증 중이다. Windows 어댑터의 내부 실행 호스트는 macOS다. 변동하는 검사 수와 후보 상태는 [검증 상태](검증-상태.md), 설치·배포 절차는 [플랫폼 빌드 상태](플랫폼-빌드-상태.md)를 따른다.

## 좌표와 효과

프로젝트의 점·사각형·다각형·이동 기록점은 **표시된 원본 전체를 기준으로 정규화한 좌표**다. 원점은 왼쪽 아래이며 `(0.5, 0.5)`는 중앙이다. PDF는 crop과 회전을 적용한 페이지, 이미지는 방향을 적용한 픽셀, 영상은 표시 변환을 적용한 프레임이 기준이다. 화면맞춤의 여백과 창 크기를 프로젝트 좌표에 포함하지 않는다.

Mac은 이 좌표를 AppKit/CoreImage 좌표로 사용한다. Windows는 Qt/Pillow의 왼쪽 위 원점으로 바꾸므로 픽셀 점은 `x × 너비`, `(1 − y) × 높이`로 대응한다. 사각형은 윗변까지 함께 변환한다. 표시 종횡비가 달라질 때 점·박스는 각 축의 비율로, 선과 지우개 폭은 두 축 비율의 기하평균으로 변환한다. 예를 들어 가로 두 배·세로 그대로이면 폭은 √2배다.

블러 반경·모자이크 크기·feather는 출력 이미지 픽셀 단위다. 창을 확대했다고 출력 효과가 강해지지 않는다. 여러 영역은 레이어 순서로 합성하되 각 효과는 원본 픽셀에서 계산한다. 그림과 글자는 영역 효과 뒤에 한 번 합성한다. 부분 지우개는 저장된 대상과 시간에만 적용하고 원본 파일을 수정하지 않는다.

Mac의 CoreImage Gaussian/Pixellate와 Windows의 NumPy·Pillow·Qt 마스크는 서로 다른 구현이다. Windows 영역 효과는 선형 sRGB·premultiplied alpha에서 필터·보간·합성하고 양자화한다. 그림은 전체 encoded premultiplied8-bit overlay에서 그리기·그림 지우개 순서를 적용한 뒤 영역 처리 결과에 한 번 선형 premultiplied 합성한다. 교차 경로는 WindingFill을 적용한다. 영역과 그림 사이의8-bit 양자화 및 서로 다른 AA 커널의 잔차는 별도 검토 대상이다. 원본의 영역 외부 바이트는 보존한다. Gaussian은 분산을 맞춘 세 번의 확장 box 근사이며 CoreImage 커널과 완전히 같지 않다.19사례의 내부/외부/시간 표본과 RGB 오차를 비교했으나 곡선 AA·feather 경계·커널 차이의 최종 허용 여부와 실제 Windows 검증은 남는다. 같은 원본에서 내부와 경계 픽셀을 따로 비교하고 실제 가림 결과를 검토해야 한다. 단순한 평균 오차만으로 민감 영역이 충분히 가려졌다고 판정하지 않는다.

## 색·투명도·글자

투명 원본10개 실제 출력 비교는6개 전체 일치,4개 잔차로 검토 필요다. 반투명 그림 내부의 Mac RGBA `[255,0,155,192]`와 Qt `[255,0,156,192]`는 정수 premultiplied 변환에서 같은117에 대응하지만 저장된 straight RGBA 값은1만큼 다르다. 지우개 경계의 최대 차이10과 블러 차이5의 전체 원인을 이 한 표본으로 확정하지 않는다. 영역 밖과 지운 내부의 원본 보존은 확인했으며, 허용오차를 임의로 정해 전체 통과로 처리하지 않는다.

저장된 그림 색은 0–1 범위 RGBA다. 그림의 alpha는 합성에 반영하고 단색 가림은 불투명하게 적용한다. 렌더링 중 premultiplied alpha와 일반 RGBA 사이 변환이 있으므로 투명 경계와 완전 투명 픽셀도 비교 대상이다.

Windows 이미지 렌더러는 유효한 색상 프로파일을 sRGB로 변환하고 RGBA8로 처리한다. Mac의 PDF/그림 합성 및 영상 출력에는 sRGB 경로가 있지만 일반 이미지의 CoreImage context와 인코더 전체에 동일한 색 처리 설정을 강제한 것은 아니다. sRGB 원본·ICC 원본·넓은 색역 원본에서 두 OS의 표시와 저장 결과를 따로 검수해야 한다. 현재 코드를 모든 입력의 색상 일치 보장으로 읽지 않는다.

글자 데이터에는 내용·글꼴 이름·굵기·박스·색·배경이 저장된다. 글꼴 파일은 프로젝트에 포함되지 않는다. 각 OS의 글꼴 배치 엔진으로 줄을 만들고 박스에 맞추므로 같은 박스에서도 한글 자형·줄 높이·가로 맞춤·배경 여백이 달라질 수 있다.

- Mac의 현재 `DrawingAnnotation.font`는 지정 글꼴을 찾지 못하면 시스템 글꼴로 대체한다.
- Windows UI는 없는 명시 글꼴을 알리고 글자 출력을 막는다. 기본/일반 글꼴 별칭은 해당 OS 글꼴로 해석한다.

이 비대칭은 남은 검토 항목이다. 프로젝트를 주고받을 때 두 OS에 실제 같은 글꼴이 있는지 확인하고, 여러 줄 한글·굵은 글자·기록점으로 크기가 변하는 글자를 비교해야 한다. 글꼴을 자동 설치하지 않는다.

문자 수는 보이는 한 글자에 해당하는 확장 grapheme 기준과 연결한다. Swift의 `String.count`와 Python의 코드 포인트 수는 결합 문자·이모지에서 다르다. shared 검증기는 ASCII 초과를 거부하고, 비ASCII가 단순 코드 포인트 한도를 넘으면 원문을 보존한 채 네이티브 grapheme 검토를 요구한다. Windows에는 Qt grapheme 검사가 있다. 이를 바이트 길이로 대신하거나 초과 이름을 조용히 잘라 저장하지 않는다. 파일명 길이와 OS 경로 제한은 별도 검사다.

## 영상 시간과 표시 변환

프로젝트의 시간은 초 단위다. 효과와 그림의 기간, 지우개 기간, 위치 기록점에 같은 재생 시각을 사용한다. `[0, 0]` 기간은 전체 적용이며, 특정 기간의 양 끝은 포함한다. 이미지/PDF에서는 영상 시각 없이 적용한다. 위치는 시간 기록점 사이에서 보간하며 FPS로 프레임 번호를 재구성하지 않는다.

Mac 미리보기·편집·생성·지우개·기록점은 실제 표시 프레임의 presentation timestamp를 기준으로 한다. 재생 슬라이더와 탐색 목표는 연속 transport 시각으로 유지하며, 아직 프레임이 없는 후보에서는 기존 목표/시각 fallback을 사용한다. 첫 paused 프레임의 정밀한 탐색은10억분의1초 단위 올림으로 프레임 앞쪽으로 내려가는 오차를 피한다. EOF에서도 편집은 실제 마지막 표시 프레임 PTS를 사용한다. 예를 들어12초/12fps/144프레임 fixture는143/12초이며 transport12초와 구분한다. VFR의 끝 시각을 이 고정 값으로 재구성하지 않는다. Mac 출력도 AVFoundation sample의 presentation timestamp를 사용한다. Windows PyAV 경로는 PTS와 time base를 사용하고 현재 구현은 원본 audio/video 시작 시각에서 재생 기준점을 정한다. 이 정책의 늦은 첫 영상·MP4 edit list 호환 검증은 미완료다. 실제500ms fixture에서 FFmpeg format duration1.0초와 Mac asset duration1.5초가 다르므로, stream start를 빼는 정책이 원래 빈 구간과 이전 Mac 기간을 없앨 수 있다. 실제 PyAV·Qt 시간축을 확인한 뒤 수정해야 하며 현재 동등하다고 보장하지 않는다. 평균 FPS는 인코더 힌트다. PTS가 없거나 진행 순서·길이를 확정할 수 없으면 오류로 처리한다. VFR의 프레임 간격, 마지막 프레임 기간, 오디오 PTS/DTS와 동기화를 유지하려는 코드가 있으나 실제 Windows 코덱 출력으로 확인하지 않았다.

Windows UI의 탐색은 새 player generation에 목표 위치를 보관하고 실제 로드·seekable·위치 확인과 explicit preview 준비 뒤 재생한다. positionChanged는 frame callback보다 늦게 올 수 있으므로 transport 위치를 프레임 PTS의 상한으로 사용하지 않는다. 원점0/CFR12/무음 fixture의 실제 Mac Qt decoder에서 앞·뒤 탐색과 다음 프레임 표시를 확인했지만 실제 Windows/PyAV의 시간원점·VFR·오디오 검증은 남는다.

Windows는 화소 종횡비와 직각 회전을 픽셀에 한 번 적용하고 새 출력의 회전 metadata를 초기화한다. 반사·크기 변환·투시 표시 행렬과 직각 이외 회전은 현재 명시 오류다. Mac은 preferred transform을 사용한다. 두 경로의 반전·확대 변환 결과, 늦은 첫 영상 PTS, Qt 재생 시각과 출력의 정렬, 재생 중 실패·취소는 아직 실제 검증이 필요하다. 해당 영상 유형의 지원 계약은 미완료 상태로 남는다.

## 프로젝트 버전·원본·재연결

| 데이터 | 현재 해석 |
| --- | --- |
| v1 | 단일 이미지/영상의 `mediaPath`, 영역, 그림. 최대20MiB. `sourceSHA256`는 선택 확장이다. |
| v2 | PDF/이미지 작업공간의 제목, 선택 페이지, 1–200페이지별 원본·독립 편집. 최대50MiB. PDF 페이지 번호는 0부터 시작한다. |
| SHA-256 | 두 버전 모두 이전 파일에는 없을 수 있다. 새 저장 경로는 원본 SHA를 기록한다. 있으면 소문자64자리로 검증한다. |
| PDF 기하 표시 | PDF 페이지의 `pdfGeometryVersion: 1`은 수정된 crop/회전 좌표다. 이미지에 붙거나 알 수 없는 값이면 거부한다. 생략은 이전 기하로 검토한다. |

원본은 JSON에 내장하지 않는다. 같은 폴더의 원본은 파일명으로 참조할 수 있고 다른 위치는 절대 경로가 저장될 수 있다. 다른 컴퓨터로 옮기면 프로젝트와 정확한 원본을 함께 준비하고 누락 원본을 직접 재연결해야 한다. POSIX 절대 경로, Windows drive 경로, UNC 경로를 구분한다. 다른 OS의 절대 경로를 현재 폴더의 정상 경로인 것처럼 해석하지 않는다. 상대 경로의 두 구분자를 처리하며 상위 폴더 탈출을 이용해 임의 원본을 찾지 않는다.

SHA가 있으면 재연결된 실제 파일과 비교하고, 디코딩 기준 파일 및 읽기 후 상태도 확인한 뒤 편집을 적용한다. 작업 중 원본 교체는 페이지 전환·저장·출력을 막는 대상이다. SHA가 없는 이전 파일의 재연결은 **원본 동일성을 입증할 수 없다**. 사용자가 그 사실을 확인하고 원본 내용과 가림 위치를 다시 검토해야 한다. 같은 이름·같은 크기라는 이유만으로 확인을 대체하지 않는다. 허용한 경로 밖을 자동 탐색하거나 원본을 전송하지 않는다.

프로젝트/출력은 새 파일로 저장한다. 기존 원본과 프로젝트를 덮어쓰지 않으며 충돌은 오류로 알린다. 후보 열기는 준비가 성공한 후 확정하는 트랜잭션이다. 실패·취소에서는 기존 원본, 페이지, 레이어, 선택과 undo/redo 및 저장되지 않은 편집을 보존해야 한다. 현재 내부 회귀가 이 경로를 검사하지만 실제 앱의 재생·파일 패널까지 완료한 증거는 별도로 필요하다.

shared의 v1/v2 wrapper는 알 수 없는 JSON 필드·배열·기본값 생략을 보존하며 검토 사유를 반환한다. Mac의 Codable 프로젝트 모델은 알 수 없는 필드의 무손실 재저장을 보장하지 않는다. 미래 필드를 포함한 프로젝트는 단순히 버전 숫자가 같다는 이유로 편집·재저장 가능하다고 판정하지 않는다.

## 이전 PDF와 HEIC/HEIF

이전 PDF 프로젝트에서 그림이나 영역이 있고 기하 표시가 없으면 raw crop/회전을 확인한다. Mac은 crop 원점이 0에서 벗어나거나, crop에 PDFKit 표시 변환을 적용한 너비·높이가 기존 크기와 다르면 재검토를 요구한다. 오차 기준은 `0.000001`이다. 원점0의 일반/180° 페이지와 정사각90° 페이지는 크기 변화가 없다. 빈 편집과 기하 표시1의 새 편집도 별도로 처리한다. 영향받은 이전 편집을 새 좌표로 자동 이동하지 않는다.

Windows의 `pdf_geometry.py`는 pypdf 원시 MediaBox/CropBox/Rotate를 읽고 Qt의 실제 표시 point 크기와 대조한다. 실제 pypdf backend가 없거나, 암호화·잘못된 box·해석 불확실성·UserUnit이1이 아닌 경우에는 확인되지 않은 기하를 허용하지 않는다. Qt 화면 크기만으로 원시 crop 원점을 추측하지 않는다. 현재 숫자 정책 검사는 통과했지만 실제 pypdf 공통 fixture 검사는 미실행이다. Mac PDFKit과 Windows PDFium의 글꼴·주석·투명도 렌더링 차이도 실제 출력 비교가 남는다.

Mac 이미지 입력은 EXIF 방향1–8을 픽셀에 적용한다. Windows 일반 이미지 입력도 방향을 정규화하며, HEIF는 libheif가 적용한 crop/회전/반전을 다시 적용하지 않는다. HEIF의 주 이미지로 작업하고 출력은 편집한 픽셀을 새로 인코딩한다. 원본 EXIF/XMP·thumbnail·다른 이미지·깊이 등 부가항목을 복사하지 않는 정책과 재열기 검사를 구현했다.

Windows HEIC 기본 출력 정책은 alpha 보존이며 완전 투명 픽셀 아래 RGB를 정리한다. 흰 배경 합성은 명시 옵션이다. Mac HEIC 출력은 새 픽셀과 방향1 metadata를 사용하지만 실제 투명 HEIC를 서로 재열어 비교하지 않았다. HEIF ICC/NCLX 변환, libheif의 방향 적용, 실제 encoder의 단일 이미지·alpha·부가항목 제외는 실제 backend 검증이 남는다.

Windows HEIF 사진의 PQ/HLG HDR 및 처리할 수 없는 프로파일은 현재 명시 오류다. 영상의 `_display_image`는 아직 `frame.to_image().convert("RGB")`를 사용하며 transfer·bit-depth별 검증/톤매핑 또는 HDR 거부를 보장하지 않는다. HEIF와 영상의 상태를 혼동하지 않는다. 실제 HDR 영상의 색·표시·출력과 Mac SDR 참조에 맞는 톤매핑은 필수 미완료 작업이다. HDR·반전/크기 변환 영상·투명 HEIC·효과 픽셀 차이에 관한 현재 오류와 미검증은 기능 지원을 축소하기로 한 결정이 아니다. 비교 원본, 실제 두 OS 출력, 차이와 해결안을 사용자에게 제시한 뒤 계약을 확정해야 한다.

## 완료 증거의 경계

| 현재 근거 | 아직 필요한 근거 |
| --- | --- |
| Mac의 실제 소스에 대한 AppKit/API 회귀, 공통 PDF 기하 내부 검수, 손상 영상 첫 프레임 실패 보존 회귀 | 현재 후보·138회귀·내부 출력 연결 완료; 실제 해당 OS 설치·사용자 실행·패널·최종 출력 수락 남음 |
| macOS에서 Windows Qt/Pillow 어댑터·shared·파일 안전성·grapheme·합성 비동기 UI 검사 | 실제 Windows의 Explorer 드롭·OS 패널·글꼴·codec·설치·재실행 |
| raw PDF 숫자 정책·fake HEIF 정책, 실제 backend 테스트와 필수 preflight 소스 준비 | 실제 pypdf·pillow-heif/libheif 검사, PyAV/OpenCV 영상 검사, Windows 포함 DLL/codec·라이선스 증거 |
| 좌표·기간·SHA 및 재연결 규칙의 구현 | Mac→Windows→Mac과 역방향의 실제 저장/재열기/수정/출력 왕복 |

내부 검사 통과, backend 누락으로 인한 skip, 빌드 스크립트 준비는 실제 Windows 또는 전체 Goal 완료 증거가 아니다. 양 OS 왕복에서는 영역의 위치·가림 결과·그림/지우개·한글·투명도·영상 기간/음성·선택 페이지와 원본 보존을 함께 확인한다.

소스 근거: Mac의 `ProjectFile`, `MultiPageProjectFile`, `PageWorkspace`, `RegionEditing`, `DrawingAnnotation`, `BlurRenderer`, 이미지/영상 exporter 및 `DocumentModel`; `shared/portable_project.py`; Windows의 `editor.py`, `renderer.py`, `video.py`, `pdf_geometry.py`, `heif_codec.py`, `ui.py`. 이 문서 작성에서는 코드·기존 검증 기록을 읽었으며 새 테스트·빌드·코덱 실행이나 설치를 수행하지 않았다.
